# Монітор стану: план імплементації v1

Дата: 2026-09-10. Статус: реалізовано в окремому worktree `bamdude-status-monitor`, гілка `feature/status-monitor`; фінальні перевірки — у [звіті](../specs/status-monitor-validation.md).

Контракт поведінки: [специфікація](../specs/status-monitor.md). Візуальний орієнтир: [макет і його запуск](../../frontend/src/mockups/monitor/README.md).

Обсяг погоджено: Принтери + Черга, спостереження/деталі/переходи до керування, авторизоване вікно **і ТВ-токен у v1**. Нижче збережено план і критерії приймання; фактичні зміни й виконані перевірки наведено у звіті.

## 1. Що вже є і чого бракує

| Є зараз | Потрібно для релізу |
|---|---|
| Ізольований макет на demo data | Production route, реальні snapshots, permission-aware моделі |
| `/camwall`, довготривалі токени з окремими scopes | Scope `monitor`, обмежені DTO, обидва ТВ-подання, scope-aware видача токенів |
| Повні status/queue API та стан усієї ферми в пам’яті | Один легкий пакетний snapshot без запитів від кожної картки |
| ETA-порівнювачі та farm forecast | Підключення до нового екрану без зміни семантики; безпечний ТВ-прогноз |
| `waiting_reason` як текст; dispatcher `message` | Структуровані коди очікування й етапи, коректне очищення та fallback |
| Виявлення stale MQTT усередині клієнта | Read-only timestamp/stale projection; окремий стан свіжості HTTP |
| Різна класифікація HMS/FAILED у різних картках | Єдина чиста класифікація для монітора за M-07–08, без глобального редизайну карток |

Послідовність: **P1 → P2 → P3 → P4 → P5 → P6**. Кожен крок має придатний для рев’ю результат. ТВ-доступ — умова завершення v1, його не можна залишити як необов’язковий follow-up.

## 2. P1 — Контракт даних і джерела станів

Місця змін: `backend/app/schemas/monitor.py` (новий), `services/printer_manager.py`, `services/bambu_mqtt.py`, `services/print_scheduler.py`, `services/background_dispatch.py`, `models/print_queue.py`, нова `mNNN_monitor_wait_reasons.py`.

- Описати типи snapshot, restricted job, waiting reason, dispatch phase; одиниці часу, nullable-поля та allowlist ТВ за M-12–16. У звичайному й ТВ DTO заборонені поля не повинні серіалізуватися випадково через наслідування повного status DTO.
- Зафіксувати перетворення `remaining_time` (хвилини) → `remaining_seconds` і відмінність від уже секундного forecast; додати приклад 5 хв = 300 с до контрактних тестів.
- Додати read-only доступ до часу останнього фактичного повідомлення та наявного stale verdict MQTT. Утримувати last-known active state лише в пам’яті; при відсутності історії повертати unknown. Не створювати timestamp на кожному GET.
- Додати `waiting_reason_code` і `waiting_reason_checked_at`: **модель + нова міграція**, nullable, без розбору старих рядків. Номер виділити з актуального списку міграцій перед реалізацією; старі міграції не редагувати.
- У місцях, де scheduler вже визначає очікування, записувати код і час. Покрити ранні виходи scheduled/manual/offline/drying/plate/stagger, маршрутизацію матеріалу, storage-full і dispatcher failure. Очищувати код разом із причиною при втраті актуальності, включно з retry/cancel/start/reorder.
- Для dispatcher додати типізований етап у runtime state поруч із чинним `message`; враховувати всі активні jobs для кожного принтера. Не міняти механізм запуску чи пріоритети scheduler.

Перевірки: нова/існуюча SQLite та PostgreSQL, повторне застосування міграції; unit-тести встановлення/очищення причини, відсутнього telemetry timestamp, stale verdict та кількох dispatcher jobs. Регресійні тести запуску/черги підтверджують, що додавання метаданих не запускає друк повторно й не змінює рішення про готовність.

Готово, коли кожен стан із §4 специфікації має конкретне джерело або явний unknown fallback, а код очікування не переживає причину, яка його створила.

## 3. P2 — Пакетний API і звичайні права

Місця змін: `backend/app/services/monitor_snapshot.py`, `backend/app/api/routes/monitor.py` (нові), реєстрація router у `backend/app/main.py`; точкове перевикористання helper-функцій із status/queue/forecast.

- Реалізувати `GET /monitor/snapshot?view=…`: вибірка неархівних принтерів, in-memory статуси, пакетні агрегати черг та справжні head items. Не завантажувати історію всіх завершених друків заради плитки.
- Розділити побудову внутрішнього snapshot і серіалізацію дозволених полів. Сам snapshot не викликає mutating scheduler/dispatcher методи чи повний status endpoint для кожного пристрою.
- Принтери потребують `PRINTERS_READ`; queue-поля й подання Черга — `QUEUE_READ`. Врахувати API-key permissions, рядкове ownership і приховану справжню голову черги. Для відсутнього права повертати omission/capability, а не вигадану порожню чергу.
- Прогноз авторизованого режиму отримувати зі штатного `/queue/forecast`. Не включати simulation у 5-секундний snapshot.
- Окремо перевірити зовнішній активний друк, відсутню чергу/телеметрію, обслуговування, архівний принтер, зміну черги під час побудови відповіді. Snapshot має час формування, але не обіцяє транзакційну синхронність MQTT і БД.

Перевірки: integration-тести 0/1/50 принтерів; permissions/ownership з різними власниками head item; SQL query count для 1 і 50 пристроїв без лінійного N+1; spies на керувальні сервіси підтверджують відсутність побічних ефектів GET. Не використовувати виклики реального обладнання в тестах.

Готово, коли API самодостатній для обох подань і відповідає M-12–15; права перевіряє сервер, а не лише UI.

## 4. P3 — ТВ-scope, видача й обмежені API

Місця змін: `services/long_lived_tokens.py`, `core/auth.py`, `api/routes/auth.py`, `api/routes/monitor.py`, `schemas/monitor.py`, frontend `api/client.ts`, `components/settings/CameraTokensPanel.tsx`, обидві локалі.

- Додати scope `monitor` до дозволених scopes, **не** до `STREAM_SCOPES`. Наявна колонка scope — рядок, тому саме нове значення не потребує міграції. Якщо реалізація додає будь-які інші колонки, потрібна окрема модельна зміна й міграція.
- Зробити авторизацію create/list/revoke у `/auth/tokens` залежною від scope. Зберегти камерні правила; для monitor виконати M-16. Сервер фільтрує списки за правами, перевіряє власника при revoke. Додавання option у UI без серверного gate не є завершенням.
- Новий verifier повертає перевірений token record/власника, а не просто bool. Перевірити активність і чинні права власника, строк дії та відкликання при кожному запиті. Не кешувати позитивну авторизацію на весь строк токена.
- Реалізувати `/monitor/kiosk/snapshot` і `/monitor/kiosk/forecast` з Bearer-токеном. Спільна агрегація з P2, але окремий allowlist серіалізації. Forecast використовує той самий simulator; повертає тільки агрегати за принтером.
- Розширити поточну панель токенів: Monitor scope, пояснення доступних даних усієї ферми, строк, copy TV URL, list/revoke. Копіювання секрету доступне лише в момент створення; згодом показати метадані та дію перевидачі через створення нового токена.
- Фрагмент URL читає тільки ТВ-клієнт; встановити no-store/no-referrer, не включати secret у cache keys та повідомлення помилок. Зберегти наявне обмеження частоти запису `last_used_at`.

Перевірки: розширити `backend/tests/unit/services/test_long_lived_tokens.py` та `backend/tests/integration/test_long_lived_tokens_api.py`; додати integration-тести kiosk API. Повна матриця: правильний/чужий scope, expired/revoked, inactive/deleted owner, втрата прав власником, недостатні права видачі, власник/інший користувач/адміністратор при відкликанні. Перевірити, що monitor-токен не працює для camera/overlay/camwall/звичайного status/queue/WS/control API і навпаки. Зафіксувати точний набір ключів у ТВ DTO, перевірити вкладені структури та відсутність довільного тексту з назвами файлів.

Готово, коли обидва ТВ-подання читають дані без сесії користувача, а видача monitor-токена не розширила старі scopes чи права CAMERA_VIEW.

## 5. P4 — Чиста модель плиток, порядок і сценарії

Нові frontend-модулі: `features/monitor/types.ts`, `state.ts`, `sort.ts`, `fixtures.ts`; unit-тести в `src/__tests__/features/monitor/` відповідно до чинної конфігурації Vitest.

- Нормалізувати snapshot у view model: основний стан, вторинні факти, увага, свіжість, ETA confidence, видимість деталей. Класифікація не залежить від React, мережі або локалізованого тексту.
- Реалізувати пріоритети M-07–11, включно з чергою на паузі під час друку, FAILED без HMS, muted HMS, plate-clear guard і historical failed count. Стан черги не підміняє стан принтера.
- Підключити наявні ETA-порівнювачі через адаптер типів; додати обробку loading/error/partial estimate зовні порівнювача. Не змінювати глобальний `etaSort.ts`, якщо це не окремо погоджена зміна поведінки всього застосунку.
- Додати незалежні grouping/search/attention filter та підрахунок унікальних ID. Побудувати таймер перестановки й утримання порядку під час keyboard focus/pointer interaction.
- Перенести сценарії макета як тестові fixtures нової моделі; demo gallery залишається лише в макеті. Додати відсутні складні перетини, а не лише окремі кольори.

Мінімальна таблиця тестів:

| Вхід | Очікування |
|---|---|
| 14, 5, 7 хв + idle + offline | 5, 7, 14; idle/offline після друку |
| Severe HMS + PAUSE + plate clear | Серйозна помилка головна; факти паузи й столу не загублені |
| RUNNING + queue paused | Прогрес зберігається, подання Черга жовте |
| RUNNING + pending count 0 | Зелений друк і вторинне «Черга порожня», не вільний принтер |
| FAILED без HMS; plate clear on/off | Очищення / зупинено; не автоматична червона аварія |
| Відома тривалість + unknown prints | Часткова оцінка, не «вільний» і не точна обіцянка |
| Прихований справжній head + наступний власний | Restricted head, не підміна черги |
| Один принтер із двома тегами | Два входження, один унікальний принтер у лічильнику |
| Poll success + stale MQTT | Сервер доступний, телеметрія цього принтера застаріла |
| Snapshot ще немає / forecast впав | Loading / прогноз недоступний; не offline/free now |
| Раніше RUNNING → offline / offline без історії | Увага під час роботи / нейтральний offline |

Готово, коли всі стани та порядок можна перевірити незалежно від верстки, а існуючі ETA-тести залишаються зеленими.

## 8. Межі рев’ю та завершення

Серверні частини P1–P3 можуть потрапляти окремими змінами без кнопки, яка веде на незавершений екран. Вхід у монітор стає доступним після інтеграції P5; реліз v1 — після P6 з обома способами доступу.

Не включати в цю роботу загальний рефакторинг PrinterCard/QueueCard, зміну ETA у старих сторінках або логіки автозапуску. Якщо виявлено неможливість отримати окремий точний стан, спочатку зафіксувати прогалину контракту й показати unknown; не підміняти її даними макета чи аналізом англійського exception message.

Результат для рев’ю: source + міграція + тести, screenshots, фактичний звіт A-01–10, production build та документація. Функція вважається завершеною лише після перевірки ТВ-обмежень, відкликання токена і незалежної роботи обох вікон.
